# 存储契约体检报告（做第二家实现顺出来的）

写 kbstore-pgvector 的第一目的不是"多一个存储引擎"，是**证伪**：v4 说存储引擎可替换，
但只有 kbstore-es 一个实现时，契约里混进了多少 Elasticsearch 的形状是看不出来的。

结论先说：**这 8 个操作的契约基本站得住**——照抄一份、换个后端实现，平台侧一行没改就跑通了
（建库 → 分批写入 → 向量/关键词检索 → 过滤/时间范围 → mget → 浏览 → 删文档 → 删库，
`store_live_test.go` 对着真 pgvector 全绿）。下面是硌到手的地方，按"值不值得改契约"分档。

## A. 契约没写、但两家都必须遵守的**隐含保证**（该补进契约文档）

1. **`mget` 必须按请求的 id 顺序返回。**
   平台把返回序当真（父块 + 窗口邻居按序组装）。ES 的 `_mget` 天然保证请求序，
   SQL 的 `WHERE id = ANY($1)` 完全不保证——第二家实现里这是要专门写代码还原的。
   契约里一个字都没提；只有一个实现时，这条保证是"免费"的，所以没人写下来。
   > 顺带：本仓这条用例第一版是假绿的——请求序恰好与写入的物理序一致，
   > 去掉还原代码也不红。改成请求序与写入序**相反**才咬得住。

2. **`kb_create` 必须幂等。** 平台侧不保证只调一次。ES 是 `PUT index` 撞了报 400 要吞掉，
   pgvector 这边是 `CREATE TABLE IF NOT EXISTS`。契约没写"幂等"，两家各自猜对了。

3. **分批写入的 `append` 语义。** 只有每篇文档的**第一批**是 `append=false`（= 覆盖该 doc）。
   契约字段注释里有，但它是**平台侧的切批行为**决定的——属于必须写进契约正文的那类，
   不然第二家实现很容易把每批都当覆盖，表现是"长文档只剩最后一批"。

4. **读路径不回流 `embedding`。** 契约把 `embedding` 声明在 `Chunk` 上（写入要用），
   但检索命中若把它带回来，每条都要背几 KB 浮点穿 NATS。ES 版靠 `srcFields` 白名单排除，
   本插件靠读列清单里不含它。契约没说，两家又是各自猜。

## B. 确实带着 ES 味道、但可接受的地方

5. **`datetime` 是字符串。** ES 直接吃 ISO 串，SQL 得 `NULLIF($n,'')::timestamptz`
   （空串转 timestamptz 直接报错）。这是小事，但它说明契约的类型是按 ES 的宽容度定的。

6. **`fields` 是无结构 map。** ES 那边是动态 mapping，天然合适；关系库这边只能整块进 JSONB，
   于是过滤一律 `fields->>'x'`，**索引与类型都退化**（数字字段做不了范围过滤、排序按文本序）。
   契约本身没错，但"元数据字段声明（`MetaField.type`）"在 pgvector 实现里几乎没用上——
   要用起来就得按声明建生成列 + 索引，那是下一步的事。
   **2026-10-04 补：数组字段**——契约的 Filter 语义是「字段可为标量或标量数组，任一元素相等即命中」（ES 的 terms 天然如此）。
   此前 `fields->>'x' = ANY($n)` 对数组只拿到 JSON 文本，永远不命中；现为 `fields->>'x' = ANY($n) OR fields->'x' ?| $n`，
   `fields` 列加 GIN 索引（老库在下一次 kb_create 时补上）；反选包 `COALESCE(…, false)`，缺字段的行保留（与 ES must_not 一致）。
   **2026-10-08 补：范围过滤**——Filter 加 `gte` / `lte`（SDK v0.7.6 能力位 `range_filters`）。能解析成数字的边界按数值比，
   且只让 JSON 数字参与（`CASE WHEN jsonb_typeof(...) = 'number'`，文本值不会撞到 `::numeric` 转换失败）；其余按文本比——平台把日期
   统一成 YYYY-MM-DD 再发，文本序就是日期序。没有走索引（数据量大时是全表过滤，与上面「类型退化」同一笔账）。

7. **`recency`（时效加权）本插件未实现** → **已按建议改掉契约（2026-08-11）**。
   ES 有 `distance_feature` 一把梭，PG 要自己写衰减表达式并入排序。当时契约**没有"能力声明"的位置**，
   插件只能静默忽略那个入参——平台既不能降级也不能提示，用户配了时效加权、界面一切正常、
   结果里毫无体现。那比"不支持"更坏：它把一个明确的限制变成了查不出来的怪现象。
   现在：SDK 加 `SetCapabilities`（常量 `sokel.CapRecency` 等，避免拼错字符串），
   随注册握手上报 → `plugins.capabilities`（迁移 0099）→ 出到插件 DTO；
   KB 保存配置时踩到「明确声明不支持」的能力会**明确警告**（不阻止保存——换个存储引擎它就生效了）。
   口径：**未声明 = 不判**（老插件不会因为这套机制上线就集体冒警告）；
   **false 必须上报也必须出到 DTO**（「明确不支持」与「没声明」是两回事）。
   本插件自报：`keyword_bm25:false, recency:false, time_range:true, field_boosts:true`。

## C. 与 ES 的真实能力差距（选型必须知道，不是契约问题）

8. **关键词腿弱。** Postgres 自带分词器对中文无能为力（`simple` 按空白切，一句中文
   就是一个巨型 token，`to_tsquery` 命中率近 0）。本插件用 **pg_trgm 相似度**替代 BM25：
   中英混排都能给出有意义的排序，但召回质量弱于 ik，长查询尤甚。
   要在 PG 上做像样的中文 BM25，得装 zhparser / pg_jieba——那是部署要求，
   不该由插件偷偷假设。**中文为主且关键词腿重要的库，仍应选 ES。**

## 结论

要动契约的只有第 7 条（能力自报，**已做**），其余是**文档债**：把 A 组四条隐含保证写进契约正文，
第三家实现就不必再靠猜。第二家实现的价值恰恰在这儿——它把"只有一个实现时看不见的东西"
变成了一份清单。
