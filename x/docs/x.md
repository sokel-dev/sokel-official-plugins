# X（推特）

发推、发推串、传图传视频、点赞转推、搜索与时间线、私信、列表，以及**被提及 / 关键词命中时触发工作流**。

## 先看这一条：X 的 API 要花钱

2026 年 2 月起 X 取消了免费档，改成**按次计费**（预付额度，用一次扣一次）：

| 动作 | 单价（官方口径） |
|---|---|
| 读一条推文 | 约 $0.005 |
| 发一条推文 | 约 $0.015（正文带链接约 $0.20） |
| 查一个用户 | 约 $0.010 |

所以：

- 读类操作的「最多几条」**不要随手调大**，一次 100 条就是半美元。
- 事件源的轮询间隔默认 300 秒、下限 60 秒。盯关键词时每轮都是一次计费的搜索。
- 402（没额度）会被翻译成人话报出来，不用去猜。

## 配置：建 app → 配平台 → 授权

**1）在 [developer.x.com](https://developer.x.com) 建一个 App**

- User authentication settings 里打开 **OAuth 2.0**；
- **Type of App 选 Web App / Automated App**（保密客户端，才会给你 Client Secret）；
- **App permissions 选 Read and write**（要发私信就选 Read and write and Direct message）；
- Callback URI 填平台的回调地址，**与下面 `X_OAUTH_REDIRECT_URL` 一字不差**：
  `https://<你的平台域名>/api/v1/credentials/oauth/callback`

> ⚠️ App permissions 改了之后**必须重新授权**，光改设置对已有令牌无效——
> 症状是所有写操作 403，而 X 的原文不会告诉你是这件事。

**2）平台侧配置**（管理员做一次，所有工作空间共用）

```
X_OAUTH_CLIENT_ID=...
X_OAUTH_CLIENT_SECRET=...
X_OAUTH_REDIRECT_URL=https://<平台域名>/api/v1/credentials/oauth/callback
X_OAUTH_PROXY=http://127.0.0.1:7897   # 平台连不上 x.com 时必填
```

**3）建凭证 → 点「授权」**，在 X 的同意页上点 Authorize app 即可。

授权会一次性申请这些作用域（X 不支持增量授权，少一个就得所有人重来一遍）：
`tweet.read tweet.write users.read like.* bookmark.* follows.* list.* dm.* media.write offline.access`。

`offline.access` 是命门：没有它就没有刷新令牌，令牌两小时后失效且无法自愈。

**4）如果插件进程连不上 x.com**，在凭证里填「出站代理」。按凭证配而不是靠进程级
`HTTP_PROXY`——后者是全局的，会把内网调用一起带偏。

### 增量拉取：游标存数据表

四个列表型读操作（搜索 / 用户时间线 / 提及 / 列表时间线）是**增量流形状**，
和其它增量流插件（公告、监管文件等）完全一致：

```
[定时触发] → [数据表·取游标] → [搜索推文] → [随便你接下游] → [数据表·写回游标]
```

传入 `cursor`（推文 id），只会拉比它更新的；返回 `next_cursor` 与 `has_more`。
`has_more` 为真表示这批拉满了，应当**立刻再拉一次**而不是等下一个定时。

没有新内容时 `next_cursor` 原样返回传入值——不会把进度冲掉。

> 为什么不用 X 自己的 `next_token`：它一小时就失效，且只在一次搜索会话内有效。
> 存进数据表下次再用必然报错。

### 盯一批账号：用列表，不要逐个拉时间线

把要盯的账号加进一个 X 列表（「列表加成员」可以自动化这一步），然后只调一次
「列表时间线」。盯 30 个账号时，这是 1 次请求 vs 30 次请求的差别——按次计费下，
差的是账单不是耐心。

### 转推与回复

搜索结果里**大半是转推**。每条推文都带 `kind` 字段（`original` / `replied_to` /
`retweeted` / `quoted`），这是插件从 `referenced_tweets` 推出来的（X 不直接给）。
只要原创就在查询式里加 `-is:retweet`，或在下游按 `kind` 过滤。

### 发推串

「发推串」把多段文本逐条发出、后一条自动回复前一条。**它不替你断句**——
一项就是一条推文，超长的那条会被 X 拒掉。

中途失败**不回滚**（前面几条已经在公开时间线上了，删掉是二次破坏）：
错误里会带上已经发出去的 id，出参 `ids` 也是「实际发出的那几条」。

### 媒体

「上传媒体」→ 拿到 `media_id` → 绑到「发推文」的媒体 id 上。视频会自动分片、
并等到 X 转码完成才返回：FINALIZE 之后立刻拿去发推会得到「media not found」，
看起来像 id 错了，其实是还没转完。

用途要选对（发推用 / 私信用）：X 按 `media_category` 校验，填错要到发布那一步才被拒。

## 事件：被提及 / 关键词命中

在**凭证**里配（事件源是常驻进程，它没有节点配置）：

| 字段 | 说明 |
|---|---|
| 监听提及 | 填 `on` 则有人 @ 授权账号时触发 |
| 监听的查询式 | X 搜索语法，如 `"我的品牌" -is:retweet lang:zh`；留空 = 不监听 |
| 轮询间隔（秒） | 默认 300，下限 60 |

两个事件（被提及 / 关键词命中）的公共字段是 `post_id` 与 `text`，平台把它们平铺到
触发输入顶层——接「发推文」回复时绑一个变量就够。

**首次启动不推历史**：接一个用了十年的账号，工作流会被几千条提及瞬间冲垮。
第一轮只记下当前位置，从此往后的才推。

> 为什么是轮询而不是实时推送：X 的 filtered stream 与 Account Activity API
> 只在 Enterprise 档（$42,000/月起），自助档拿不到。

## 常见问题

**403 但看不出为什么**——按这三条排查（插件已把它们写进错误信息里）：
① App permissions 不是 Read and write，或改了之后没重新授权；
② 授权时少了作用域（如发私信要 `dm.write`）；
③ 这个操作要更高档位——**引用转推**和**全量存档搜索**都是 Enterprise 专属。

**429 限流**——错误里会写「几点恢复」（X 的 `x-rate-limit-reset` 是绝对时间戳）。
搜索/提及是 15 分钟 300 次，发推是 15 分钟 100 次。

**搜不到 7 天前的内容**——自助档的搜索只有最近 7 天，这是 X 的限制，不是插件的。

**私信发不出去**——对方没关注你、且没有开放「接收任何人的私信」时，X 一律拒绝。
