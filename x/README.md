# x — X (Twitter) read/write and event-trigger plugin

Post/thread/media, like/retweet/bookmark/follow, search and timelines, direct messages, lists —
**22 operations** in total; plus **2 events** (mentioned / keyword matched) as workflow trigger
sources.

The user-facing manual is [docs/x.md](docs/x.md) (reported during the handshake; what shows up
under "usage notes" in the UI is exactly this file). This file is for whoever works on this plugin:
why it's shaped this way, where the pitfalls are, what the integration points are.

## Design decisions

The benchmark is n8n's X node (Make dropped its native X module in 2025-04, Zapier deprecated
theirs back in 2023, so n8n is the only one left worth copying from). It has 8 actions: post/reply,
delete tweet, search, like, retweet, send DM, look up user, add list member. The five points below
are **tradeoffs made on top of that**, not stylistic preference:

1. **Reads use the platform's incremental-stream shape, not a copy of X's pagination.** X's
   pagination is `next_token` — it expires in an hour and is only valid within a single search
   session. A workflow's pattern is "run every hour, continue from last time"; storing `next_token`
   in a data table is guaranteed to error on the next run. So externally it's `cursor` (since_id) in,
   `next_cursor`/`has_more` out — the same shape as other incremental-stream plugins; `next_token` is
   only used internally for auto-pagination within a single call. **An empty result still returns
   the cursor as-is**, so progress is never clobbered.

2. **Retweets and replies must be distinguishable at a glance.** Most of a search result is
   retweets, and X doesn't give you a field for "what is this". `kind` (original / replied_to /
   retweeted / quoted) is derived from `referenced_tweets`; otherwise downstream would have to guess
   from an `"RT @"` prefix.

3. **A thread is one operation.** X has no thread endpoint — threads are chained one `in_reply_to`
   at a time. On the canvas that would be N nodes + N connections; editing the copy once means
   touching N places, and a break in the chain is untraceable. A mid-thread failure **doesn't roll
   back** (the earlier tweets are already public), but the ids already posted appear both in the
   error and in the `ids` output.

4. **Media upload is its own operation.** It's a three-stage initialize/append/finalize flow plus
   transcode polling; folding it into the post operation would saddle even "post plain text" with
   chunking logic. Splitting it out makes it an explicit canvas step that can be retried on its own
   if it fails.

5. **Normalization is done entirely in the plugin.** X dumps authors, media, and quoted tweets into
   `includes` and links them by index; referencing `includes.users[3].username` on the canvas could
   never be stable. Every outgoing tweet carries its own `author_username`, expanded media, and
   **outbound links expanded to their real addresses** (the body only has t.co short links, which
   are useless downstream).

## Auth: OAuth is the only path

X's write operations require a user identity, and `client_secret` is held by the platform, so there's
no "just paste a key and go" option. The `access_token` on the credential is injected by the
platform (the plugin never touches `refresh_token`).

Scopes **must all be granted in one go** (X doesn't support incremental authorization — missing one
means making everyone re-authorize from scratch); see `schema.Credential.AuthMeta`. `offline.access`
is the critical one: without it there's no refresh token, and the access_token expires in two hours
with no way to recover.

The platform added two generic capabilities for X (`server/internal/credential/`):

- **PKCE** (required by X): `code_verifier` is never stored or put in a URL — state carries a nonce,
  and the verifier is derived independently on each side via `JWT.DeriveKey("oauth-pkce:"+nonce)`
  (`oauth.go::pkceFor`).
- **refresh_token rotation** (X issues a new one on every refresh and invalidates the old one
  immediately): `preauth.go::enrichOAuth` persists the new one and serializes per refresh-token hash
  with a lock. Skipping this shows up as "authorization works fine today, then every call 401s two
  hours later".

## Event source

X's real-time push (filtered stream / Account Activity) is only available on the Enterprise tier,
not on the self-serve plan, so this polls instead. **What to watch is configured on the credential**
(the event source is a long-running process, with no per-node configuration):
`watch_mentions` (on/off) / `watch_query` (X search syntax) / `poll_seconds` (default 300, floor 60).

Four rules, the first three learned from the notion/gmail event sources:

- **Never emit history on first start** (connecting a ten-year-old account would instantly flood the
  workflow) — just record the current position;
- **Write the cursor back to the credential** (`watch_cursor`, one per stream), otherwise a restart
  either re-emits everything or misses changes made while the process was down;
- **Stop right where a push fails**, don't advance the cursor, retry next round (prefer duplicates
  over loss — the platform side deduplicates);
- **The interval has a floor** — X charges per read, and an accidental 10-second poll turns into a
  bill for tens of thousands of calls a day.

⚠️ **Single replica only**: multiple replicas would each advance the same cursor independently,
causing duplicate pushes and the cursor jumping back and forth.

## Cost (X dropped its free tier starting 2026-02)

Reading one ≈ $0.005, posting one ≈ $0.015 (with a link ≈ $0.20), looking up a user ≈ $0.010.
Because of this: `me()` is cached per access_token (querying it on every single operation would be
pure waste), read operations default their "how many" to 50, and the event source defaults to a
300-second interval. A 402 (insufficient quota) gets translated into a human-readable message.

## Deployment

```bash
# 1) Platform: install X on the plugins page -> create a nats access group -> copy the skp_ token
# 2) Start the replica (this directory's docker-compose.yml; SOKEL_ENDPOINT / SOKEL_TOKEN come from the environment)
docker compose up -d
# 3) Platform environment variables (used for changing/refreshing the token)
#    X_OAUTH_CLIENT_ID / X_OAUTH_CLIENT_SECRET / X_OAUTH_REDIRECT_URL / X_OAUTH_PROXY
# 4) Create a credential -> click "authorize"; if x.com isn't reachable, set an outbound proxy on the **credential**
```

**Two proxy settings, two different values**: the platform runs on the host, so it uses
`http://127.0.0.1:7897`; the plugin runs in a container, so the credential needs
`http://host.docker.internal:7897` (127.0.0.1 inside the container is the container itself). The
plugin's proxy is configured per credential rather than via the container's `HTTP_PROXY` — the
latter is global and would also drag the broker connection's traffic through the proxy.

## Development

```bash
go generate ./...          # must run after editing the schema
go build ./... && go vet ./... && go test -race ./...
```

Tests use a fake upstream (`x_test.go`), pinning down **the things that aren't visible anywhere
else**: normalization, cursor semantics, thread chaining and interruption, media chunk ordering,
`x-rate-limit-reset` being an absolute timestamp rather than a number of seconds, and the three
causes of a 403.

Changing the contract also means checking these integration points beyond this directory (see
`docs/dev-playbook.md` §4.4 / §5 for details): `server/internal/api/seed.go::seedFirstPartyPlugins`
(the directory listing), `internal/api/plugin_test.go::TestListPluginsSeeded` (the count), and this
directory's `docker-compose.yml` (deployment).

## What's not implemented

- **Quote retweet** has an endpoint, but X put it behind the Enterprise tier — calling it on the
  self-serve plan 403s, and this is documented in the contract.
- **Full-archive search** (`/tweets/search/all`) is likewise Enterprise-only; only the 7-day recent
  search is implemented.
- **Spaces / Communities / Trends / analytics data**: no workflow use case yet — add it when there is one.
- **Bulk fetching of follower/following lists**: at per-call pricing, an operation like this costs
  tens of dollars in a single run — revisit once there's a concrete use case.
