# Qdrant

Connect Sokel to your own Qdrant instance to manage dense-vector collections, write points, retrieve payloads, run similarity queries and scroll through points. Qdrant can run locally or on your own server; no cloud account, paid service or external embedding provider is required. Supply embeddings generated by your own workflow. This is a direct database integration; configuring the platform knowledge-base storage backend is a separate task. This release was exercised against Qdrant 1.20.0 and follows its REST API.

## Deployment and credentials

Set the required deployment environment variable `SOKEL_QDRANT_URL` to the Qdrant REST service URL, for example `http://qdrant:6333` or `https://vector.example.internal/qdrant`. There is no default service or public fallback. The URL may use HTTP for an internal deployment and may include a reverse-proxy path prefix. It must not contain a username, password, query, fragment or dot path segments. HTTPS is appropriate when traffic crosses an untrusted network.

In a container, `localhost` refers to that container. Use a reachable service name on the container network, or a host address configured for your deployment; pointing the plugin at its own `localhost` will not reach a separate Qdrant container. Configure the REST port, not the gRPC port. The plugin does not install or start Qdrant.

Enter **API key** in the credential form if the instance requires one. Leave it blank only for an instance intentionally configured without authentication. The key is sent in the `api-key` header. Grant collection read access for read operations and the appropriate write permissions for mutations. Key provisioning and rotation happen outside this plugin.

`health_check` reads the collection list. It returns `ok` and `message`, and returns `ok=false` on configuration, transport or authorization failure. It confirms collection-list access, not write permission or readiness of every collection. It does not create data.

## Operations

| Operation | Inputs and result |
| --- | --- |
| `health_check` | Verify the configured service and collection-list access. |
| `list_collections` | Return collection names. This endpoint returns one complete list subject to the response-size limit; it has no pagination input. |
| `get_collection` | `collection`; return name, status, optional approximate point/indexed-vector counts and `config_json`. |
| `create_collection` | `collection`, `size`, `distance` and optional `vector_name`; create one unnamed or named dense-vector configuration. Returns `created=true` only when Qdrant confirms creation. |
| `query_points` | `collection`, a numeric `vector`, optional `vector_name` and `options`; return IDs, optional payload JSON and similarity scores. |
| `upsert_points` | `collection`, 1–256 typed `points` and optional `vector_name`; write IDs, vectors and optional payloads. Return a completed write receipt. |
| `retrieve_points` | `collection` and 1–256 `ids`; return matching points plus `missing_ids`. Missing IDs are a normal result. |
| `scroll_points` | `collection` and optional `options`; return one point page, `next_offset` and `has_more`. |
| `delete_points` | `collection` and 1–256 explicit `ids`; delete those IDs and return a completed write receipt. No filter-based bulk deletion is exposed. |

Collection inputs accept 1–255 ASCII letters, digits, hyphens or underscores. The listing may show other names, but this release cannot address names outside that subset. Dense vectors must contain 1–65536 finite numbers and match the collection dimensions. Distance is one of `Cosine`, `Euclid`, `Dot` or `Manhattan`. A named vector is a separate configuration within a collection; use the same name for creation, writes and queries. Sparse vectors, multivectors and automatic inference are outside this release.

## Point IDs, payloads and writes

Every point ID is a **string** in Sokel: either a canonical unsigned 64-bit decimal string, including `"0"`, or a hyphenated UUID. Decimal IDs are sent as exact JSON integers; UUIDs are sent as strings and normalized to lowercase. IDs such as `"18446744073709551615"` are preserved without floating-point conversion. Duplicate IDs within one request are rejected.

For example, after creating a collection with `size=3` and `distance=Cosine`, upsert:

```json
{
  "collection": "books",
  "points": [
    {"id": "0", "vector": [1, 0, 0], "payload_json": "{\"title\":\"Example\",\"available\":false}"},
    {"id": "76874cce-1fb9-4e16-9b0b-f085ac06ed6f", "vector": [0, 1, 0]}
  ]
}
```

`payload_json` is an optional JSON object string because payload fields are defined by your application. `{}` is valid; a JSON array or null is not. Payload objects and returned collection configuration remain JSON strings so arbitrary nested fields and large integers are preserved. Null or absent payloads remain absent. Read operations deliberately request payloads and omit stored vectors.

Upsert replaces an existing point with the same ID; it is not a partial payload update. Use it only when the supplied record represents the point you intend to store, particularly on collections with several named vectors. All vectors in a batch must have equal dimensions. Writes use `wait=true` and an upstream timeout of 30 seconds. The plugin accepts a point-write receipt only when its status is `completed`; `acknowledged` is not reported as completion. An operation ID may be absent. Completion does not report how many supplied IDs existed before deletion.

## Querying and scrolling

`query_points.options` accepts `limit` (default 10, 1–1000), `offset` (default 0, 0–1000000), optional `score_threshold` and optional `filter_json`. Explicit zero values are preserved. Score and threshold interpretation depends on the distance metric. `filter_json` is a Qdrant filter object string; the plugin validates its JSON structure and Qdrant validates its filter semantics. For example:

```json
{
  "collection": "books",
  "vector": [1, 0, 0],
  "options": {
    "limit": 10,
    "score_threshold": 0,
    "filter_json": "{\"must\":[{\"key\":\"available\",\"match\":{\"value\":false}}]}"
  }
}
```

Vector query returns one ranked result page, not a complete-record export or a total count. Use `scroll_points` to traverse points by ID. Its options are `limit` (default 100, 1–1000), optional `offset` and optional `filter_json`. Omit `offset` initially. While `has_more=true`, pass `next_offset` exactly as `options.offset`, keeping the collection and filter unchanged. The offset may be `"0"` or a UUID, so do not parse it as a floating-point number. Qdrant's `next_page_offset=null` ends traversal. Missing or repeated continuation metadata fails the operation. Concurrent writes can change results; scrolling is not a snapshot.

## Limits and failures

Payload/filter JSON objects are limited to 512 KiB each. HTTP requests are limited to 1 MiB and responses to 8 MiB. Reduce batch/page sizes for large vectors or payloads. Calls have a 45-second transport timeout within the 60-second operation deadline; point operations request a 30-second server timeout. Qdrant's own storage, memory, access and query limits still apply.

The plugin rejects redirects, uses only the configured service and does not retry failed HTTP responses or replay mutation request bodies. It does not echo raw upstream error bodies, service URLs or credentials. HTTP errors, non-OK Qdrant envelopes, malformed receipts and invalid pagination fail explicitly. After a timeout, inspect the collection or point before repeating a write: it may already have been applied.

This release does not delete collections, manage aliases/snapshots/shards, update payload indexes, run arbitrary API requests or manage cloud accounts. The chosen operations work with the self-hosted open-source server. Tests include both documentation-derived synthetic wire fixtures and recorded responses from a disposable local Qdrant 1.20.0 container, with no production account or data.
