# Claude Code

把**本机装的 Claude Code** 接进工作流：给它一个 GitLab 项目和一句任务，它在真实工作树里
改代码，过程实时回传，结论与改动清单进下游节点。

## 一、部署前提

这个插件**必须跑在同时满足三条的机器上**：能访问你的 GitLab（自建的多在内网）、
装了 `claude`、磁盘装得下仓库。它不是随便哪台机器都能部的——和 Kubernetes 插件同类。

## 二、两处配置，分工是一条线

**凭证回答「用谁的额度」，环境回答「这台机器能干什么」。**

凭证里只有一项：

| 字段 | 怎么填 |
|---|---|
| Anthropic API Key | **可以留空**。留空 = 用那台机器上 CC 自己的登录态（订阅制常见）；填了 = 这次调用走这把 key 的额度（多空间分账、要审计时用）。两种都是合法部署 |

其余全是部署这台机器时设的**环境变量**，工作流作者不该、也不需要碰：

| 环境变量 | 作用 |
|---|---|
| `SOKEL_CC_GIT_BASE` | GitLab 根地址，如 `https://git.example.com` |
| `SOKEL_CC_GIT_TOKEN` | 克隆/推送令牌。**不设就用这台机器上 git 自己的认证**（credential helper / `.netrc` / SSH）——那样令牌根本不进插件进程，更干净 |
| `SOKEL_CC_WORKSPACE` | 仓库与工作树放哪，默认系统临时目录下 |
| `SOKEL_CC_CLAUDE_BIN` | `claude` 路径，默认从 PATH 找 |
| `SOKEL_CC_ALLOW_EXTERNAL_DIRS=1` | 允许「继续任务」指定工作区之外的目录（默认不允许）|
| `http_proxy` / `https_proxy` | CC 出站代理——**CC 自己就读这些标准变量**，插件不转发。git 那边会主动剥掉（内网仓库不能走代理）|

**为什么这么分**：GitLab 地址和令牌曾经也在凭证里，那是错的——同一个令牌得在 gitlab 插件
和这里各配一份（轮换时必漏一处），换台机器部署还要去改凭证。更要紧的是，凭证是**工作流
作者**在画布上选的，而机器能访问哪些目录、走哪个代理，该由**运维**定。

配好点「检查凭证」：会显示 Claude Code 版本、工作区、GitLab 是否可达。

## 三、典型用法

两个节点串起来：

```
[Claude Code · 执行任务] ──→ [GitLab · 建 MR]
```

CC 只管改代码推分支，开 MR 交给 gitlab 插件——各管一段，出问题时也分得清是谁的。

**任务描述越具体越好，把验收标准写进去**：

> 修复 `internal/api` 里 alert 分页越界的问题，并让 `go test ./internal/api` 通过

比「修一下分页」有效得多——它会自己跑测试验证，而不是改完就说完事了。

跑完想追加一句（「测试没过，再改改」），用**继续任务**：把出参里的 `session_id` 和
`branch` 传进去，它记得上一轮做过什么，在同一个工作树上接着改。

## 四、看得到过程

任务操作是流式的：CC 边干边把文字推上来，画布的运行面板边跑边长；跑完整段过程也在出参
`log` 里。跑十分钟的节点不该只有「执行中」三个字。

## 五、人接管一个跑起来的会话

工作流跑到一半想自己接手（它方向不对、或者你想手把手带一段），可以：

```bash
cd <出参里的 worktree>
claude --resume <出参里的 session_id>
```

**三个前提，缺一不可**：

1. **同一台机器**——会话存在插件那台机器的 `~/.claude/projects/<工作目录转义>/<会话id>.jsonl`，
   不跟着网络走。
2. **同一个系统用户**——会话文件是 `0600`，只有跑它的那个用户读得了。
   插件如果跑在专用服务账号下（推荐），你得用那个账号登录才能接管。
3. **会话还在**——插件没开 `--no-session-persistence`（默认就没开），文件就一直在。

接管之后再交回工作流也行：**会话 ID 不变**（除非用 `--fork-session` 分叉），
下次「继续任务」传同一个 ID 就接着走。工作树是同一份，你手改的东西它也看得见。

### 反过来：插件接管你起的会话

也成立，而且是**两个方向里更常用的那个**——你在终端里跟 CC 弄了半天，想把后续
（跑测试、改一轮、发通知）交给工作流：

1. 部署这台机器时设 `SOKEL_CC_ALLOW_EXTERNAL_DIRS=1`（默认不允许，见下）
2. 「继续任务」填 **会话 ID** + **直接指定工作目录**（你那个仓库的绝对路径），
   项目/分支留空

CC 按 id 在整机范围内找会话，不限目录，所以你在哪儿起的都能接管。

**为什么要开关**：这个入参让编排工作流的人可以把 CC 指到那台机器上**任意**目录——
爆炸半径从插件工作区扩到整机。闸门放在**部署环境**上而不是入参上：装这台机器的是运维，
编排工作流的是业务，该由前者决定后者能指到哪儿。

**接管外部目录时不支持推送**：那个仓库的远端和分支归你管，插件猜一个推上去太危险——
改动留在目录里，你自己 `git push`。

> 每次「执行任务」跑完，日志最后一行就是拼好的接管命令，照抄即可。

## 六、出参怎么用

| 出参 | 用途 |
|---|---|
| `conclusion` | CC 的最终答复——「它做了什么、结果如何」。给人看/给下游 LLM 判断 |
| `changed_files` / `diff` | 改了什么。接条件节点判「有没有改动」最直接 |
| `branch` / `pushed` | 接 gitlab 插件建 MR 用 |
| `cost_usd` / `turns` | 这次花了多少。接告警/统计 |
| `session_id` | 给「继续任务」，也是人接管时 `--resume` 的参数 |
| `worktree` | 代码改在哪个目录。人要接管就 cd 到这儿 |
| `denied_tools` | **任务没做完时先看这里**——非空说明它想做但被权限拦下了，多半是权限配窄了 |

## 七、管理本地的工作树与会话

跑久了这台机器上会堆下工作树和会话，用两个操作看和清：

**列出工作树**——先看再删。每项给：项目 / 分支 / 路径 / 占用 MB / 最后活动 / 闲置天数 /
**有没有未提交改动** / 会话数 / 最近会话 ID（`claude --resume` 直接能用）。

**清理工作树**——两种用法：
- 点名删一个：给项目 + 分支
- 批量清：给 `idle_days`（如 14），可再加 `project` 限定范围

三道保险：
1. **既不点名分支、又不给闲置天数会被拒绝**——那等于「删光所有工作树」，这种要求得说出口
2. **默认保护有未提交改动的**（`include_dirty` 关着）。删掉就没了
3. `dry_run` 先看会删哪些

**会话不会被删**。CC 的会话在 `~/.claude/projects/` 下，是 CC 自己的存储，不归这个插件管——
删工作树只回收代码目录。会话文件很小，真要清理请自己动手，那样也不会误伤你在同一台机器上
手工跑的其它会话。

## 八、坑

- **默认不推代码**：改完只回 diff 和结论，代码留在工作树里。要 push 得显式打开——
  让一个 agent 默认握着 push 权限，是那种出事之后才被发现的默认值。
- **成本一定要给上限**：`max_budget_usd` 是 agent 跑飞时唯一的刹车。不给的话，
  告诉你它跑飞了的会是账单。
- **权限模式**：默认 `acceptEdits`（能改文件、常规文件命令放行）。
  `bypassPermissions` 等于把这台机器交出去，只在隔离容器里用。
- **同名分支复用同一个工作树**：第二次跑更快，但它也看得见上一轮的改动。要干净起点就
  换分支名，或先用「清理工作树」。
- **工具过滤是冒号语法**：`Bash(git:*)`，不是 `Bash(git *)`。
- **一个分支同时只跑一个任务**：两个任务共用一个工作树必然互相踩。
