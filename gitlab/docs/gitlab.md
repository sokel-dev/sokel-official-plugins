# GitLab

把 GitLab 接进工作流：读写仓库文件、建/评/合 MR、开 Issue、查流水线与失败日志、
触发构建。**自建 CE 与 gitlab.com 都支持**——凭证里填实例地址即可。

## 一、准备凭证

1. GitLab 头像 → **Preferences → Access Tokens** → 创建个人访问令牌，
   scope 勾 `api`（只读场景勾 `read_api` 即可）。
2. 凭证里：**GitLab 地址**填自建实例根地址（如 `https://git.example.com`，
   留空 = gitlab.com）；**访问令牌**粘进去。
3. 建议专建一个机器人账号出 token，按需给项目角色（Reporter 够读，
   Developer 能提交/建 MR，Maintainer 能合并保护分支）。

自签 HTTPS 证书的自建实例：把 CA 挂进插件容器的系统信任，否则连接失败。

## 一.3、找东西

**搜索**：搜代码 / Issue / MR / 提交。留空项目 = 全实例搜——agent 找「这个函数在哪儿用过」
最直接的入口。各类命中归一成同一个结构（代码给 `path`/`line`/`snippet`，Issue 给 `iid`/`title`），
画布上不用为「搜的是什么」准备两套下钻路径。

> 大实例上全局搜代码可能很慢，能限定项目就限定。

## 一.4、让 agent review MR

- **MR 改动**：拿到改了哪些文件、每个文件的 diff——**让 agent review 用的就是它**。
  单文件 diff 超过上限会截断，`truncated` 会告诉你；**按文件截断而不是整体截断**，
  一个几万行的迁移不该把其余文件的改动一起挤掉。
- **改 MR** / **批准 MR**：改标签、关闭、投批准票。批准是**以凭证那个账号的身份**投的，
  别让 agent 替人做决定。
- **MR 行级评论**：把 review 意见落到具体某文件某一行。你只给路径、行号、内容——
  定位需要的三个 sha 由插件自己去 MR 上取（让人在画布上填 base/start/head 是不可能填对的）。
  评论被删掉的行时改用「原文件行号」。
- **MR 有新评论** 事件：在 MR 下说一句就能让 agent 接着看。与 Issue 评论是两个事件——
  GitLab 那边走同一种 Note 事件，插件按 `noteable_type` 分流。

## 一.5、让 agent 自己收尾

处理完之后要能收口，否则同一个 Issue 会被反复触发：

- **改 Issue**：关闭 / 加减标签 / 指派。**处理完摘掉触发标签（如 `claude`）、打上 `cc-done`，
  是防重复触发最干净的办法**——比在流程里记「这个我处理过了」可靠得多。
  只填要改的字段，留空的不动。
- **改评论**：长任务应该**先回一条「处理中…」、跑完更新同一条**，而不是刷两条。
  既好看，也少一次「评论触发」的成环机会。用「评论 Issue」出参里的 `note_id`。

## 二、操作速查

- **project 字段双形态**：数字 ID 或路径 `group/name`（仓库地址里域名后那段），
  所有操作同一规则。
- **写文件（提交）**：文件不存在自动 create、存在自动 update；配合
  `start_branch` 可以「切新分支 → 提交 → 建 MR」一条流走完。
- **合并 MR**：CI 未过/有冲突时 GitLab 拒绝（报错说明原因）；勾「等流水线过了再合」
  可以交给 GitLab 自动合。
- **Job 日志**：拿失败 job 的日志尾部 → LLM 总结失败原因 → 发群，CI 排障闭环。
- **通用调用**：typed 没覆盖的（releases/tags/webhooks/成员管理…）照 API 文档
  直调，路径不带 `/api/v4` 前缀。

> **翻页看 `has_more`，别看条数**：列表都回 `total`（全部条数）和 `has_more`（还有下一页）。
> 正好 50 条不代表翻完了；而超大结果集上 GitLab 会省略总数，那时 `total=0` 但 `has_more` 仍准。

## 三、事件触发（起工作流）

两条路，按时效要求选：

**① 插件事件源（轮询，约 1 分钟延迟，配置最省）**：凭证里「事件盯哪些项目」
填 path 逗号分隔（如 `backend/server,infra/deploy`），保存后自动启动。五类事件：
**有新提交 / 新 MR / MR 被合并 / 新 Issue / 流水线失败**。画布上加「事件触发」
节点选 GitLab 即可。填了才轮询；不填只用普通操作零开销。

**② 插件 Webhook 入口（零延迟 + typed 事件，推荐）**：凭证行点「Webhook」生成
一条 URL → GitLab 项目 Settings → Webhooks 粘进去（Secret token 填凭证里的
webhook_secret，勾 Push / Merge request / Issues / Pipeline events）。
事件与轮询源**同一套 typed 契约**（有新提交/新 MR/MR 被合并/新 Issue/流水线失败），
画布不感知来路。**与轮询源二选一**：两条都开同一动作会各触发一次。

**「先建 Issue，再打标签」用 `issue_labeled`**：加标签在 GitLab 那边是一次 *update*，
不是 open，所以 `issue_opened` **不会**再响。要「先提 Issue，看一眼再决定派不派活」，
监听 `issue_labeled`——它带 `added_labels`（本次新增的）和 `labels`（当前全部）。
**判该不该派活用 `added_labels`**：`labels` 是全量，随便加个无关标签也会让它含 claude。
两条路都支持：webhook 从 `changes.labels` 取；没配 webhook 的部署由轮询自己比对
（首轮只记位置，不会把存量带标签的 Issue 全灌成运行）。

**在 Issue 下评论就继续派活**：监听 `issue_commented`。它带 `comment`（这次说了什么）
和 `author`（谁说的）。

> ⚠️ **这个事件天然会成环**：机器人回复 Issue 也是一条评论 → 又触发一次 → 无限循环。
> 工作流里**必须**加两道防线：条件节点滤掉机器人账号（判 `author`），
> 并且只认以 `/cc` 之类前缀开头的评论（判 `comment`）。少一道都可能烧钱烧到你发现为止。

多轮接续：上一轮的会话 ID 可以用 Claude Code 插件的**「列出工作树」**拿到——
按 `cc/issue-<编号>` 找到那份工作树，出参 `last_session` 就是它，喂给「继续任务」
即可接着上一轮改（它记得之前做过什么）。不需要额外的存储。

**Issue 事件带正文与标签**：`description` 是 Issue 正文（要把 Issue 内容交给下游干活时，
用的就是它——标题往往只是一句话），`labels` 是标签数组。**拿标签当闸**：只处理打了某个
标签（如 `claude`）的 Issue，比「谁建的都跑」安全得多。轮询源会多取一次详情来填这两个字段。

**③ 工作流级 Webhook 触发器**：工作流入口直接收原始 JSON，字段自己下钻——
只在需要插件没覆盖的事件类型时用。

## 四、常用组合

- **CI 失败告警**：「流水线失败」事件 → Job 列表 → Job 日志 → LLM 摘要 → 飞书/短信。
- **自动开单**：监控发现问题 → 建 Issue（带标签、指派）→ 评论跟进。
- **配置变更流**：写文件（start_branch 切新分支）→ 建 MR → 人工审批节点 → 合并 MR。
- **变更监控**：定时 → 提交列表（since=上次时间）→ 有新提交 → 通知/触发构建。

## 五、排错

| 报错 | 处理 |
|---|---|
| GitLab 不认这个 token（401） | 过期/吊销，重新生成；scope 至少 api |
| token 权限不够（403） | 账号要在项目里且角色够（合并要 Maintainer） |
| 找不到（404） | **没权限的项目 GitLab 也回 404**（防探测）——先确认 token 的账号在项目里，再核对路径 |
| 连接失败 | 自建实例确认插件容器网络可达；自签证书要挂系统信任 |
| 拒绝合并（405） | CI 未过、有冲突或分支保护，MR 页面上看卡在哪 |
